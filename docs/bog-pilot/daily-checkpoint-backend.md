# Daily reports and checkpoints: backend adapter contract

This S07 slice provides private models, domain services and seven version-1 operation classes. The application controller, routes, serializers, registry entries and next literal tool catalog belong to root integration. These keys must not become participant-available until that catalog is sealed and the real runtime approves it. No source document is automatically a daily purchase or savings contribution.

The caller uses `HouseholdFinance::Operations::Runner.new(household, user: authenticated_user)` with `operation_key`, `input`, and an opaque `idempotency_key`. All seven classes require the authenticated actor and sensitive audit handling. Input includes `cohort_id`; actor, enrollment identity, approval sequences, heads, support, calculations and completion metadata are selected on the server. Unsupported input keys fail. JSON money uses exact integer cents. Dates use ISO `YYYY-MM-DD`; the enrollment's frozen `Pacific/Guam` calendar applies.

All version/head comparisons are explicit. First changes send `expected_version_id: null` and `expected_head_lock_version: 0`. Corrections send the current immutable version ID and head lock version shown by a freshly authorized read. Financial corrections additionally require a nonblank reason of at most 500 characters. Pending corrections leave the old approved version current. Approvals use the draft's captured base version/head lock, its current `lock_version`, and explicit `accepted: true`. Reusing a key means replaying exactly the original request, including its original locks; replays reauthorize their private subject.

Purchase `disposition` defaults to `purchase`; amount is 1–2147483647 cents, merchant is a nonblank string of at most 120 characters, and splits are 1–20 explicit active household categories whose integer amounts sum exactly to the purchase. `link_kind` is `manual_new` or `existing_transaction`. The latter requires the household's existing confirmed/reconciled canonical transaction ID and its reviewed 64-character SHA256 digest from `SavingsChallenge::Daily::CanonicalPurchase.digest(transaction)`. Amount, merchant, splits and purchase date must match its canonical facts; a reviewed source authorization date may be used while posted date remains separate. Linking does not create another actual. A second logical daily head for the same participant cannot link that same current canonical actual. Separate physical purchases of identical amount/date/merchant remain separate.

An approved manual correction creates a replacement canonical actual and marks the prior owned actual ignored, retaining its positive amount/date/category history. Source-owned or otherwise externally linked facts cannot be edited or voided by this path. A void has `disposition: "void"`, `amount_cents: 0`, `splits: []`, `link_kind: "manual_new"`, the existing approved manual `purchase_id`, original merchant/date and an explanation. It appends an immutable void version and ignores the owned prior actual. It does not create a zero-valued actual. A voided head cannot be reused; a later real purchase needs a new head. Future in-window purchases may be staged, but actual approval must happen on or after the effective local date; a promise does not automatically become money tomorrow.

Check-in states are exactly `spending`, `no_spend`, `unknown`. There is one stable personal check-in head per local day, with immutable revisions. Several personal purchases can share that day. A missing report is unknown; a no-spend report is an explicit attestation. No-spend conflicts with current approved purchases of this participant: correct that check-in explicitly before approving a purchase, or approve a participant-owned manual void before accepting no-spend. Partner household purchases do not silently establish this participant's daily spending. All-account completeness remains unknown. Backfills require explicit dates and cannot exceed the elapsed personal window.

Feelings are optional strings of at most 500 characters or null. Saving them appends separate reflection history, never financial or check-in history. Reflection may accompany an unapproved purchase draft; that creates no actual. Later reflection updates never move the purchase date. Erasure removes text from every historical reflection version and leaves only tombstone metadata; immutable financial history stays intact. The self-only household owner/partner erasure exception remains available during a program hold, withdrawal or removed cohort membership. It grants no reads, new text or financial mutation, and never permits another participant's erasure. User revocation or loss of writable household membership denies erasure. The erasure response must contain only completion/tombstone identity metadata; its Runner subject supports private replay, but must not be serialized into a financial/calendar/history read during that exception.

Private reads use `SavingsChallenge::Daily::ParticipantReader.new(enrollment, user: authenticated_user).page(collection, limit: 20, after_id: nil, parent_id: nil)` or `.find(collection, id:)`. Every call reauthorizes the current membership, frozen enrollment identity, household role and real runtime. Collection symbols are `purchases`, `purchase_drafts`, `purchase_versions`, `reflections`, `reflection_versions`, `check_ins`, `check_in_versions`, `checkpoints`, `checkpoint_drafts`, `checkpoint_versions`. Limit is 1–100; ascending ID cursor is stable and `next_cursor` is null at the end. Parent filters apply only to version/draft collections. Results contain scoped ActiveRecord objects for an explicit private serializer; do not expose raw generic `attributes` or share them in household/coach read paths. Root must whitelist fields and convert IDs/locks without substituting client claims.

`SavingsChallenge::Daily::DayProjection.new(enrollment, user:, local_on:).call` returns the ISO local date, personal report scope, state, check-in IDs/lock/completion time, approved purchase count, nullable reported spend, changed canonical-link flag, no-spend discrepancy and unknown all-account completeness. An independently changed canonical actual makes current reported spend unknown until explicitly reconciled. No feelings appear in this projection.

Checkpoint milestones are 30, 60 or 90, with cutoff `starts_on + milestone_day - 1`. Before that local date they cannot be staged or approved. Stage freezes the current savings approval sequence and separate daily financial/check-in sequence, then produces `savings_checkpoint_v1`. Approval rejects changed sequences, draft/head locks, invalid calculations or baseline identities. Reflection changes do not change those sequences. Approved versions and predecessors remain immutable.

The first snapshot selects a target accepted by local cutoff-day end, within the captured savings approval sequence. An explained checkpoint revision retains its original plan, even if the current target changed. A different accepted plan requires both `plan_version_id` and `plan_correction_accepted: true` on a revision; its selection is labeled `explicit_correction`. This changes no financial facts. The server-only `SavingsChallenge::Projection` plan selector is not a public projection query argument.

An optional baseline is a real immutable `FinancialBaselineVersion`, scoped to the household and enrollment participant with verified snapshot digest. Complete/partial/manual coverage and supported calendar-month count are retained as approved facts. Later source changes do not rewrite that frozen baseline or claim fresh evidence support. Absence reports `not_provided` and `unlinked`, never complete. Savings evidence allocation remains a separate root extension; this slice neither invents supported cents nor infers spending cuts caused savings.

Checkpoint snapshot fields are calculation_version, milestone_day, cutoff_on, captured_at, time_zone, accepted_cohort_release_id, financial_approval_sequence, daily_approval_sequence, plan_selection, savings, baseline, daily, final_confirmation_status. The savings object is the existing exact-cent projector output. Daily summaries include immutable purchase/check-in version IDs and aggregate personal reporting counts and nullable spending, never feelings. Final confirmation is `not_applicable` for Day30/60, or `pending`/`confirmed` for Day90. Only explicit `final_confirmation_accepted: true` confirms it. Missing final confirmation does not erase known savings progress, change it to zero, or declare failure. Day91 money does not enter a Day90 snapshot. Root UI/reporting must keep arithmetic achievement separate from final confirmation and evidence support.

Internal `CheckpointSnapshot` calculations require the caller's authorized locked enrollment; public adapters go through the operations or private reader. `validate!` recomputes the captured financial/daily histories and validates calendar/release/plan/baseline identities before approval. These services provide backend evidence for selected DAILY/CHECK/CLOCK/PRIV cases. They do not complete the pilot UI, coach grant model, retention policy, live deployment review or full acceptance matrix.
