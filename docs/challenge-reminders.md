# Challenge reminders and source expiry

This S09 backend adds durable daily reminders in the primary database. In-app is enabled by default. Email requires separate participant consent and explicit operator configuration; WhatsApp delivery is not included. The notification contains a generic invitation to open the app. It contains no amount, merchant, feeling, statement, savings result or private link.

Reminders use the enrollment's pinned `Pacific/Guam` timezone and inclusive personal start/end dates. The scheduler considers only today's local day after the approved prompt time and outside quiet hours. It does not backfill missed prompts after an outage. A dismissed or previously delivered notification is not recreated for that enrollment/day/channel. Neither dismissal nor delivery failure records a check-in, spending, no-spend, known zero or participant inactivity.

## Participant operation and read contracts

`reminder.preference.set` and `reminder.dismiss` are version 1 operations under `HouseholdFinance::Operations::Reminders`. Both declare `ACTOR_REQUIRED` and `SENSITIVE_AUDIT`, take `new(household, user:)`, and return an immutable `ChallengeReminderEvent`. Root registers them in the shared Registry and frozen tool catalog. Replay accepts only an exact event belonging to the current household and participant actor; current writable membership and participant role are checked again.

Preference input is exactly `{enrollment_id, channel, enabled, local_time, quiet_start, quiet_end, policy_version, expected_preference_id, expected_lock_version}`. Channels are `in_app` and `email`; enabled is a boolean; times are local `HH:MM`. Policy is `generic_daily_reminder_v1`. The default prompt is `18:00`; quiet hours run from `21:00` through `08:00`. Equal quiet endpoints mean no quiet interval. Virtual defaults have a null ID and lock version zero; actual records require their current ID/lock. A competing preference save conflicts rather than overwriting it.

Dismiss input is exactly `{enrollment_id, reminder_id, expected_lock_version}`. Only an enrollment-owned, delivered in-app notification can be dismissed. Dismissal updates notification state and appends the private decision event; it does not create daily attendance. Disabling either channel remains available after withdrawal or runtime hold, subject to current participant/writable household authorization. Enabling requires an active enrollment and current accepted challenge runtime. Disabling cancels pending/leased work for that channel; it does not recall delivered email or previously downloaded copies.

`ChallengeReminders::Domain.new(household, user:).read(enrollment_id)` returns only `enrollment_id`, pinned timezone, both preference records/defaults, the current undismissed generic in-app reminder, the operator email enablement state, and `dismissal_is_check_in: false`. Preferences expose ID/lock/channel/enabled/local and quiet times/policy. The reminder exposes ID/lock/local date/title/body/public app path. The read contains no financial projection, provider credentials, delivery diagnostics, recipient or private evidence.

Root owns HTTP routes, exact serializers, private response caching, parameter filtering, account-switch cache clearing, UI disclosures and operation-status integration. The event stores the participant-approved timing/consent fields privately; general Runner audit mirrors must remain empty under the sensitive marker.

## Durable scheduling and delivery

`ChallengeReminders::Scheduler` reads active enrollments in chunks of at most 100, taking the household lock before current authorization and per-day insertion. SQL uniqueness enforces one row per enrollment/local date/channel and one preference per enrollment/channel. The immutable delivery key is a random UUID, with no participant or financial text. The primary outbox has status, generic reason code, next-attempt time, bounded attempt count and a lease token/expiry. SQL guards reject cross-participant scope, changed delivery identity, changed pinned provider namespace and resending terminal states.

`ChallengeReminders::Delivery#call` dispatches at most 100 due rows. `claim` leases one row for two minutes and increments its attempt count; `deliver_claim` fences obsolete tokens and rechecks enrollment, current household/user/cohort permission, runtime hold, channel consent, local date, quiet hours and daily attendance before making an effect. In-app availability is a database-only committed transition. Email holds the household lock through the bounded adapter request so an opt-out committed first prevents the send. An opt-out following a completed send cannot recall the copy.

Known `:not_sent` results use exponential backoff from 60 seconds, capped at 900 seconds, and at most five attempts. An uncertain email result without provider idempotency becomes terminal `unknown`. A crashed non-idempotent email lease also becomes unknown, including during quiet hours. An idempotent provider may retry the same delivery key only under the same pinned namespace; provider changes fail closed. If uncertainty remains at the final attempt, it stays unknown rather than being relabeled a known failure. `delivery_uncertain` remains visible in internal diagnostics even if pending work is subsequently cancelled. No general log contains an exception message, recipient, SMTP secret or private payload.

`Delivery.request_dispatch` treats job enqueue as optional: queue failure returns false without removing primary work. `ChallengeReminderRecoveryJob` schedules today's work, recovers expired leases and dispatches due rows directly. The recurring production entry runs every five minutes. If the entire scheduler/queue is unavailable, these services can be invoked by an operator when it returns; reminders survive as primary rows. Dispatch and recovery have total batch bounds, while enrollment scheduling uses bounded read chunks so later programs are not starved behind the first hundred.

The supplied daily-attendance interface is `completed?(enrollment:, local_on:)`. Its default returns false and suppresses nothing. Root must supply the actual S07 reader of approved daily status. Notification status, a chat timestamp, a queued job or an email failure cannot substitute for that reader.

## Disabled-by-default SMTP adapter

`ChallengeReminders::ProductionEmail` wraps `ChallengeReminderMailer`. The existing application used Resend invitation calls and had no ActionMailer/SMTP configuration to reuse. This adapter adds a scoped plain-text mailer without changing the invitation path or enabling the ActionMailer railtie globally.

Email requires `REMINDERS_EMAIL_ENABLED=true`, `REMINDERS_SENDER_VERIFIED=true`, a valid `REMINDERS_FROM_EMAIL` (fallback `MAILER_FROM_EMAIL`), a public HTTPS root `REMINDERS_PUBLIC_APP_URL` (fallback `FRONTEND_URL`), and a configured SMTP transport. The public link cannot have a private path, query, fragment, user info, nonstandard port or local/IP host. Sender verification is an operator attestation; this code does not verify DNS or provider approval. Ordinary operational release must verify the sender, approved app entry URL and delivery setup before setting these flags. Participant consent alone never activates the operator channel.

SMTP uses port 587 with mandatory STARTTLS or port 465 with TLS, certificate validation, five-second open and ten-second read timeouts. Explicit `SMTP_ADDRESS/PORT/USERNAME/PASSWORD/DOMAIN` or existing mailer transport settings provide configuration. No credential is persisted in reminder rows. SMTP declares no provider idempotency: Message-ID identifies a message but is not proof of deduplication. Unknown SMTP delivery needs operator reconciliation; no resend/reconciliation operation is exposed by this slice. The generic message has no attachment and points only to the public app entry. The mailer suppresses its own content/recipient logger.

ActionMailer's `perform_deliveries` must also be true. The adapter forces delivery errors to surface so a swallowed transport error cannot become a delivered result. Disabled operator configuration or mailer delivery prevents dispatch.

A future trusted provider adapter implements `enabled?`, `supports_idempotency?`, `idempotency_namespace`, and `deliver(recipient:, delivery_key:, message:)`, returning `:delivered`, provably `:not_sent`, or an unknown result. Root must validate the provider's actual idempotency behavior and timeout before enabling it. Namespace changes do not authorize retransmission of an uncertain older send.

## Source lease sweep

`ChallengeReminders::SourceLeaseSweep` selects at most 100 originals with explicit challenge uses and no remaining unrevoked future expiry. It calls the existing S08 `SourceRetention.expire!`, which locks household then source and checks all current explicit uses again. A newly authorized later use prevents premature deletion. Originals without challenge leases retain their earlier policy.

`ChallengeSourceLeaseExpiryJob` runs every five minutes. Expiry immediately denies new raw access, erases disposable extraction evidence and creates/reuses the existing durable primary cleanup outbox. It does not call S3 or enqueue a deletion itself; the existing source cleanup recovery worker performs physical removal. Approved financial/source facts remain. Root must retain the S08 availability predicate on every raw-source GET before and after fetching/rendering, since access expires even while cleanup is delayed. Provider/backup retention and copies already downloaded remain separate disclosed limits.
